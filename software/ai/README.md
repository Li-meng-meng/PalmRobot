# ai/ — 视频处理与图片处理

> **所有 AI 都跑在上位机**（电脑端 WPF / App MAUI），机器人只负责播放动作。
> 机器人是 ESP32，既没有摄像头接口，也没有跑模型的内存和算力。

---

| 能力 | 原型（Python） | 落地（上位机） | 阶段 |

## 视频处理：提取精华，再表达

> 8 个自由度不可能复刻人体动作。做法是**从视频里提取"动作精华"，再用机器人的身体重新表达**。
> **能做的就做，做不了的就摇摆** —— 保证任何视频都能生成结果。

### 七类精华特征

| 维度 | 从视频怎么提 | 机器人怎么表达 |
|---|---|---|
| 节拍 / 速度 | 音频能量包络 + onset → BPM | 播放速率、摇摆频率 |
| 能量 / 强度 | 肢体运动速度 × 幅度 | 摇摆幅度档位 |
| 方向 | 重心偏移、躯干朝向 | 行进、转向 |
| 周期性 | 动作片段自相关 | 循环 vs 单次 |
| 高度变化 | 髋 / 肩纵轴轨迹 | 站起 / 趴下 / 俯仰 |
| 情绪倾向 | 面部表情 + 动作柔和度 | 表情切换 + 动作刚柔 |
| 段落结构 | 音乐与动作切分 | 段落切换 |

### 兜底原则

不允许出现"分析失败，无法生成"。识别质量再差，也至少靠节拍与能量生成一段律动。

## 图片处理：表情识别

**上位机摄像头 → MediaPipe Face Landmarker（468 关键点 + 52 blendshape）→ 52 维降为 12 维 → 低通滤波 + 速率限制 → 指令发送（10–20 fps）**

**不需要 Kalidokit** —— MediaPipe 原生就给出 blendshape 系数。

### 三个必须做对的地方

| 要点 | 原因 |
|---|---|
| **低通滤波 + 变化速率限制** | 原始系数抖动大，直接推会让 OLED 抖成噪点 |
| **夸张化映射** | 单色小屏表达力有限，幅度要放大 |
| 端到端 < 150 ms | 超过 200 ms 用户就觉得不同步 |

## 最重要的工程约定

> **映射表（精华特征 → 机器人动作）存成一份 JSON，Python 和 JS 读同一个文件。**
>
> 映射表是产品核心资产、一定会反复改。两边各写一份逻辑必然漂移，这是双语言方案最大的坑。
