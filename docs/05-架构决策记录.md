## ADR-01 · 部署架构：不需要任何服务器

### 决策

**全部页面由 ESP32 自己托管，不购买、不运维任何服务器。**

### 三种页面来源的对比

| 来源 | 用户怎么打开 | 离网可用 | 结论 |
|---|---|---|---|
| **① ESP32 自己托管** | 连机器人 WiFi → 打开 `palmrobot.local` | ✅ | ✅ **采用** |
| ② 免费静态托管（GitHub Pages） | 打开网址 | ❌ | ⚠️ 只用于官网/文档 |
| ③ 本地文件（`file://`） | 双击 HTML | ✅ | ❌ 摄像头打不开 |

### 为什么方案 ② 不能做控制台

- GitHub Pages 强制 HTTPS
- **HTTPS 页面连接局域网 `ws://192.168.x.x` 会被浏览器当混合内容拦截**
- Chrome 还在收紧"公网 HTTPS 页面访问局域网 IP"的策略，这条路只会越来越窄

而反过来是**允许**的：HTTP 页面加载 HTTPS 资源（CDN 上的 three.js / MediaPipe）没问题，HTTP 页面连 `ws://` 同源机器人也没问题。

> **所以"页面由 ESP32 托管"一举解决三个问题：CORS、混合内容、离线可用。**

### 官网与产品页分开

| 页面 | 托管 | 用途 |
|---|---|---|
| 官网 / 文档站 | GitHub Pages（免费） | 介绍、教程、动作包下载、购买链接 |
| 控制台 / AI 页 | **ESP32 内置** | 遥控、预览、表情、OTA |

官网的 HTTPS 页面**不需要连机器人**，所以混合内容问题不存在。

## ADR-02 · 用户如何打开页面（配网与访问路径）

### 完整流程

```
① 首次开机，机器人没存过 WiFi
      ↓
② 自动开热点 PalmRobot-A3F2（OLED 上显示这个名字）
      ↓
③ 用户手机连上热点（扫码自动连，或手动输密码）
      ↓
④ Captive Portal 自动弹出配网页（或手动打开 palmrobot.local）
      ↓
⑤ 选 WiFi + 输密码 → 机器人保存并重启
      ↓
⑥ 以后开机自动连，直接访问 palmrobot.local
```

### 三个关键设计

| 设计 | 作用 |
|---|---|
| **Captive Portal**（DNS 劫持 + 302） | 连上热点后手机**自动弹配网页**，用户连地址都不用敲 |
| **mDNS 域名** `palmrobot.local` | 比记 IP 友好得多 |
| **OLED 显示热点名 / IP** | 用户不用翻说明书 |

### 辅助手段

- 随附卡片印二维码：WiFi 连接码（`WIFI:T:WPA;S:...;P:...;;`）+ 网址码
- 机身贴纸印网址
- （可选）NFC 贴纸

### 配网状态机（必须做对）

| 状态 | 行为 |
|---|---|
| 首次开机 | 开热点，OLED 显示"请连 PalmRobot-XXXX" |
| 配网中 | 保持热点，页面显示"正在连接…" |
| 配网成功 | 重启进 STA 模式 |
| **连不上（换 WiFi / 改密码）** | **自动退回 AP 模式**，提示重新配网 |
| 恢复出厂 | 长按按键 5 秒 / 连续上电 3 次 |

> **"连不上自动回退"最关键** —— 否则用户换了路由器就永久卡死，只能返厂。这是很多便宜 IoT 设备的通病。

### 为什么不做 App 配网

| 方式 | 需要 App | 结论 |
|---|---|---|
| **Web 配网 + Captive Portal** | ❌ | ✅ **采用** |
| SmartConfig / ESP-Touch | ✅ 要 App | ❌ |
| BLE 配网 | ✅ 要 App | ❌ |

> 配网一辈子只做一次。为了省这一次操作而让用户先装 App，是本末倒置。

## ADR-03 · 算力分工：手机是大脑，机器人是身体

### 决策

| 任务 | 跑在哪 | 理由 |
|---|---|---|
| 舵机控制、步态播放 | **机器人（ESP32）** | 实时性要求毫秒级，走网络就废了 |
| 表情渲染 | **机器人** | 只是几何绘制，且要与动作同步 |
| 配网、参数设置 | **机器人**（内置网页） | 数据量极小 |
| 拍照、姿态/表情识别、视频→动作、3D 预览 | **手机 / PC** | MediaPipe 模型几 MB，ESP32 既放不下也跑不动 |

**判断标准：需要实时反馈的放机器人，需要算力的放手机。**

### 关键推论：图片根本不传给机器人

| 内容 | 数据量 | 传给机器人？ |
|---|---|---|
| 视频帧 | 几 MB/秒 | ❌ **完全不传** |
| 人体姿态关键点 | ~1 KB/帧 | ❌ 手机内部消化 |
| 12 维表情参数 | ~50 字节/帧 | ✅（10–20 fps ≈ 1 KB/秒） |
| 一个动作包 `.motion` | 2–10 KB | ✅ 一次性 |

**差了三个数量级。** 机器人从头到尾不知道"视频"是什么。

### 白送的好处：隐私

视频帧**从未离开手机**，所以可以直接把"**视频画面不出手机**"写成卖点，而不是负担。

## ADR-04 · 预览分档：Canvas 2D 优先，three.js 走 CDN

### 澄清一个概念

**three.js 跑在用户手机浏览器里，不是跑在 ESP32 里。** ESP32 只是"把网页文件发给手机"。

真正要决定的是：**three.js 和模型文件要不要塞进 ESP32 的 flash？**

### 三个方案

| 方案 | 部署成本 | 离网可用 | 代价 |
|---|---|---|---|
| **A. 全塞进 ESP32**（gzip + 模型减面） | ¥0 | ✅ | 吃 300–500 KB flash，**要放弃 OTA** |
| **B. Canvas 2D 内置 + three.js 走 CDN** | ¥0 | 部分 | 需有网才出 3D |
| C. 自建静态站 | ¥0 | ❌ | 混合内容硬伤 |

### 采用方案 B，理由

**预览的目的是"看每条腿的角度对不对"，不是"看外观多精致"。**

- 内置 **Canvas 2D 侧视图**：约 5 KB，无依赖，离网可用，看角度甚至比 3D 更直观
- 有网时加载 CDN 上的 three.js，自动升级为 3D
- **真正的 3D 展示需求在内容制作**（录演示视频），那在电脑上跑，没有任何 flash 限制

### ESP32-C3 flash 预算

| 内容 | 大小 | 位置 |
|---|---|---|
| 固件 | 1.0–1.3 MB | app 分区 |
| 控制页（压缩） | 50–100 KB | LittleFS |
| 动作包 × 20 | ~100 KB | LittleFS |
| **Canvas 2D 预览** | **~5 KB** | LittleFS |
| （可选）减面 STL × 8 | 200–400 KB | LittleFS |
| three.js 完整版 | 100–300 KB（gzip） | ❌ 走 CDN |
| MediaPipe | 几 MB | ❌ **放不下** |

### 补充：真要离线 3D 也能做

gzip 预压缩（ESP32 只发字节，解压由手机做）+ 模型减面到 5% 面数，共约 300–500 KB 可塞进 flash，**代价是要选 `No OTA` 分区、放弃 OTA 升级**。

## ADR-05 · 视觉能力分级（**对已有文档的修正**）

### 修正的原因

已有文档在 C 档写了"加摄像头"、扩展件清单里写了"摄像头"，但**没有核对 ESP32-C3 有没有摄像头接口**。这是一个疏漏，必须修正。

### 事实

| 事实 | 影响 |
|---|---|
| **ESP32-C3 没有摄像头接口**（无 LCD_CAM 外设） | **无法直连 OV2640 等摄像头** |
| **ESP32-C3 不支持外接 PSRAM** | 连缓存一帧的内存都没有 |

> **结论：现主控选型（ESP32-C3 + PCA9685）与"机器人自带摄像头"互斥。**

### 即使换成 ESP32-S3，能识别什么

必须把"识别"分级，门槛天差地别：

| 能力 | 需要什么 | ESP32-S3 |
|---|---|---|
| **颜色追踪**（追红球） | 色彩阈值 + 连通域，**不需要 AI** | ✅ 轻松，30+ fps |
| **巡线** | 二值化扫描，不需要 AI | ✅ 轻松 |
| **人脸检测** | 轻量 CNN（ESP-DL） | ✅ 可以，QVGA 约 10–20 fps |
| **特定 3–5 类物体分类**（自己训练） | 小 CNN + 量化 | ⚠️ 勉强，1–5 fps |
| **通用物体识别**（杯子、遥控器…） | 主流检测模型 | ❌ **不可能** |

> **最重要的一句：ESP32 级别的 MCU 做不了"通用物体识别"，只能做"特定小任务"。**

### 三条路

| 方案 | 硬件成本 | 能做什么 | 延迟 |
|---|---|---|---|
| **A. 不加摄像头**（视觉走手机） | ¥0 | 全部，含通用识别 | 高（过网络） |
| **B. 换 ESP32-S3 + PSRAM + 摄像头** | **+¥20–30** | 颜色追踪、人脸检测、少量分类 | **低（本地）** |
| C. C3 + K210 协处理器 | +¥30–45 | 更强，能跑更多模型 | 低 |

### 决策：**默认不加摄像头；加摄像头的唯一理由是"低延迟"**

| 玩法性质 | 该用什么 |
|---|---|
| "识别这是什么物品" | **手机**（完胜） |
| "追球、跟随人、实时避障" | **必须本地**（走网络 200 ms 就追不上） |

**时机提醒**：现在还没采购，是改主控的最后时机。一旦按 C3 下单、PCB 定型、外壳开好孔，再改就要重做。

**建议**：P0/P1 先用手机方案跑通，摄像头作为 V2/V3 可选增强。理由：¥300 预算买不起摄像头方案；先用手机验证玩法，才知道哪个玩法真的需要低延迟视觉。

### 连带影响

- **C 档的摄像头建议先砍掉**，省 ¥25–35（换成 ToF/红外做避障，几块钱）
- 外壳**预留摄像头开孔**，为将来留余地
- 用手机摄像头做表情/手势识别时，**画质更好、角度更灵活、零成本**

## ADR-06 · 上位机作为一等交付物

### 决策

**新增 WPF 上位机**，与网页明确分工。详见《04-上位机技术方案》。

| 归属 | 内容 |
|---|---|
| **网页**（用户） | 遥控、播放、表情、简化版编辑、单台 OTA |
| **上位机**（内部） | 串口通信、出厂标定、批量测试、烧录、完整时间轴编辑、订单工单 |

**为什么必须有**：串口通信、批量设备管理、固件烧录、长时间老化测试、大屏动作编排——这些网页都做不了。

## ADR-07 · 未来 App 走 MAUI，用 WebView 混合

### 决策

| 阶段 | 用什么 | 说明 |
|---|---|---|
| 现在 | 浏览器网页 | 零安装、零成本 |
| **以后** | **.NET MAUI + WebView** | 把网页嵌进 App 壳 |

### MAUI 的最大障碍

**MediaPipe 没有官方 .NET 绑定**（官方只支持 Python / C++ / JS / Android / iOS）。三条路：

| 方案 | 工作量 | 评价 |
|---|---|---|
| **A. MAUI + WebView 跑 MediaPipe Web** | 小 | ✅ **推荐** |
| B. 绑 Android AAR / iOS Pod | 中 | 要维护两套绑定 |
| C. 换 ONNX Runtime + 姿态模型 | 中大 | 全 C#，但模型要自己找 |

### App 真正的价值

不是配网，而是：

1. **离网也能跑 AI** —— App 可以把 MediaPipe 打包进去（手机存储宽松，不像 ESP32 只有 4MB）
2. 更好的摄像头权限与性能
3. 推送通知、后台常驻

### 为 MAUI 铺路的关键动作（现在就做）

**把领域逻辑抽成 .NET 类库 `PalmRobot.Core`**：`.motion` 模型、通信协议、标定算法、校验逻辑。WPF 上位机现在引用它，未来 MAUI 直接复用，不用重写。
