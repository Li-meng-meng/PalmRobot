## 0. 角色边界（先划清，否则会和嵌入式互相等）

### 0.1 你负责

| 领域 | 具体内容 |
|---|---|
| 仿真 | MuJoCo 步态仿真、参数调优、仿真视频 |
| 前端 | 内嵌网页控制台、动作编辑器、用户侧 3D 预览 |
| AI | 视频动作提取、表情识别、音乐节拍 |
| 工具 | 动作包生成、出厂标定、订单采购脚本 |
| 内容 | 演示视频、技术拆解素材 |

### 0.2 你不负责（由嵌入式承担）

| 领域 | 说明 |
|---|---|
| 固件逻辑 | 动作解释器、舵机调度、姿态管理 |
| 网络服务 | ESP32 上的 HTTP / WebSocket 服务端 |
| 硬件驱动 | PCA9685、OLED、传感器 |
| 步态在实机上的移植 | 你输出参数，他负责烧进板子 |

### 0.3 交界面（最容易互相卡住的地方）

| 交付物 | 谁写 | 谁用 |
|---|---|---|
| **`.motion` 动作文件格式** | **你定义**，与嵌入式共同冻结 | 嵌入式实现解释器 |
| **网页前端（HTML/JS）** | **你写** | 嵌入式塞进固件 |
| **JSON 接口（HTTP/WS 命令表）** | **你定义** | 嵌入式实现 |
| **步态角度参数表** | 你调优输出 | 嵌入式烧录 |

> **第一周必须完成的事：把 `.motion` 格式和 JSON 命令表定死。** 你俩并行开发的前提就是这个，晚了会互相返工。

## 2. P0 任务清单（0–2 月，≈ 25 人天）

这个阶段的唯一目标：**让 Gate 1 通过**（裸机能走 1 米不摔 + 悬崖检测有效 + 手机可控）。

### T1.1 MuJoCo 环境搭建与模型加载

| 项 | 内容 |
|---|---|
| 交付物 | 一个能跑起 sesame 四足模型的 Python 脚本 + 环境说明 |
| 具体内容 | 装 MuJoCo；加载 `sesame-ml/assets/mjcf/sesame.xml`；在 `viewer` 里看到机器人 |
| 验收 | 运行脚本后模型出现，关节能通过代码控制 |
| 工时 | **2–3 天** |
| 依赖 | 无（不需要硬件） |
| 备注 | 模型是现成的，不要自己建模 |

### T1.2 步态仿真与参数调优 ★核心任务

| 项 | 内容 |
|---|---|
| 交付物 | ① 可用的步态参数表（JSON）② 仿真走路视频 ③ 调参记录 |
| 具体内容 | 先在仿真里实现站立 → 原地踏步 → 直线行走；找到一组稳定的角度序列与周期参数 |
| 验收 | 仿真中连续走 2 米不摔；参数表能被嵌入式直接使用 |
| 工时 | **8–10 天** |
| 依赖 | T1.1 |
| 备注 | **这是 P0 最耗时也最重要的任务**。仿真里调稳了，实机成功率才高 |

### T1.3 定义 `.motion` 动作格式 + Python 生成/校验工具

| 项 | 内容 |
|---|---|
| 交付物 | ① 格式规范文档（1 页）② `motion_gen.py`（生成 + 校验） |
| 具体内容 | 按总纲 7.2 定义 JSON 结构；写脚本能生成动作、校验合法性、导出给固件 |
| 验收 | 嵌入式能按这份规范写出解释器；生成的样例动作能在仿真里播 |
| 工时 | **2 天** |
| 依赖 | 无 |
| 备注 | **必须第 1 周完成**，它阻塞嵌入式 |

### T1.4 内嵌网页控制台

| 项 | 内容 |

| 交付物 | 单页 HTML（内嵌到固件用） |
| 具体内容 | 连接 ESP32 热点后打开 `192.168.4.1` 即可控制；按钮触发动作、切换表情、显示电量 |

| 依赖 | 与嵌入式约定 HTTP/WS 命令表（T1.3 同期） |
| 备注 | 不需要框架，原生 HTML + fetch/WebSocket 即可 |

### T1.5 three.js 用户侧动作预览

### T1.6 表情 12 维参数调试面板

## 6. 优先级与串行关系

### 6.1 必须串行的

```
T1.3（格式定义）→ 嵌入式解释器 → 一切动作相关功能
T1.1（仿真环境）→ T1.2（步态）→ 实机走路 → Gate 1
T1.3 → T1.5（预览）→ T2.1（编辑器）→ T3.4 / T4.1
T3.1（节拍检测）→ T3.3（视频律动 L1）→ T4.1（L2）
```

### 6.2 可以并行的

| 组合 | 说明 |
|---|---|
| T1.4 网页控制台 ‖ T1.2 步态仿真 | 一个偏前端、一个偏算法，互不阻塞 |
| T1.6 表情面板 ‖ T1.2 | 同上 |
| T3.2 表情镜子 ‖ T3.1 音乐打拍 | 两条独立玩法线 |

### 6.3 优先级排序（资源不够时按此顺序砍）

| 优先级 | 任务 | 砍掉的代价 |
|---|---|---|
| **P0 必做** | T1.3 格式 / T1.1 仿真 / T1.2 步态 / T1.4 控制台 | 砍任何一项 Gate 1 都过不了 |
| **P0 尽量** | T1.5 预览 / T1.6 表情面板 / T1.7 演示片 | 砍了不影响验收，但影响内容与体验 |
| P1 必做 | T2.1 编辑器 / T2.2 标定工具 | 没有标定工具量产会崩 |
| P1 尽量 | T2.3 脚本 / T2.4 体验 / T2.5 文档 | 影响效率与口碑 |
| P2 首选 | **T3.1 音乐打拍** / T3.2 表情镜子 | 这两个是 V2.0 的传播点 |
| P2 次要 | T3.3 / T3.4 / T3.5 / T3.6 | 可延后 |
| 后期 | V2.5 / V3.0 全部 | 前面赚到钱再说 |

## 9. 风险与应对

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| S1 | **`.motion` 格式反复改** | 嵌入式返工 | 第 1 周冻结，之后只加字段不删改 |

| S5 | 硬件延期 | 你无事可做 | 前期全部任务都不依赖硬件，可继续推进 |
| S6 | 只有你一个人做软件 | 排期翻倍 | 按 6.3 优先级砍，先保 P0 必做 |
| S7 | 低端手机跑不动 MediaPipe | 用户流失 | 抽帧降采样；提供"降级为纯节拍"模式 |

## 10. 明确不做（防止范围膨胀）

| 不做 | 原因 |
|---|---|
| 打包成 App（安卓/iOS） | 网页够用，打包是纯成本 |
| 账号系统 / 用户中心 | V2.0 阶段完全不需要 |
| 自建云服务 | 动作包用文件分享即可，别养服务器 |
| 在 P0 做任何 AI 功能 | 先把"能走"做出来，AI 是 P2 的事 |
| 3D 建模 | 模型现成，你不需要画（见《分角色技术方案》第 8 节） |
| 自研物理引擎 | MuJoCo 现成 |
| Unity / 大型框架 | 控制面板用原生 HTML 就够 |
| 复杂的动画曲线编辑器 | 先做表格版，用户真用起来再升级 |

## 11. 第一个月的最小成功定义

如果一个月后只能交付三样东西，应该是：

1. **`.motion` 格式规范**（解锁嵌入式）
