## 1. 背景与目标

### 1.1 背景

Sesame 是一个优秀的开源迷你四足：ESP32 主控、8 个舵机（每腿 2 个）、0.96" OLED 表情屏、3D 打印外壳，官方物料成本 50–60 美元。

我们的目标是在保留"能走 + 有表情 + 可联网"的前提下，做两件事：

1. **把物料成本压到最低**（已在本 PRD v1.0 完成测算）
2. **把"可玩性"做成产品主线** —— 让它不只是一个能走的玩具，而是一个能"学你动作、学你表情"的互动伙伴

### 1.2 三层目标

| 层级 | 目标 | 衡量方式 |
|---|---|---|
| 硬件层 | 极限版物料成本 ≤ ¥115 | 实价采购清单核算 |
| 软件层 | 手机/电脑可完成动作编排、表情镜像、视频律动 | 端到端可用 |
| 玩法层 | 至少 6 种可反复玩的玩法，其中 2 种依赖 AI 能力 | 用户可独立玩通 |

### 1.3 非目标

- 不做 12 自由度版本（本期）
- 不做激光雷达 / SLAM / 自主导航
- 不追求人体动作的逐关节复刻（做法是**提取动作精华再表达**，见 8.1.2）
- 不做量产开模

## 3. 产品定义与形态

### 3.1 一句话定义

一只**掌心大小、能走能演，还能学你动作精华和表情**的开源四足桌面机器人。

### 3.2 产品由三层构成

| 层 | 载体 | 职责 | 是否必需 |
|---|---|---|---|
| **本体** | 四足机器人（ESP32 + 8 舵机 + OLED） | 执行动作、渲染表情、联网通信 | 必需 |
| **伴生应用** | 手机 / 电脑 | 视频与表情的 AI 处理、动作编排、遥控 | V2 起必需 |
| **云端** | 可选服务 | 大模型对话、动作包市场 | 可选 |

> **关键结论：AI 玩法不增加硬件成本。** 视频分析和表情识别都跑在手机/电脑上，机器人只负责播放动作，因此 V2.0 的玩法升级是**纯软件投入，¥0 硬件增量**。这也是本产品相比"堆硬件"路线的核心差异。

### 3.3 形态与规格目标

| 维度 | 目标值 | 说明 |
|---|---|---|
| 外形尺寸 | 最长边 ≤ 150 mm | 掌上级 |
| 整机重量 | ≤ 450 g | 与 8 个 9g 舵机匹配 |
| 驱动方式 | 8 舵机 / 8 自由度（每腿 2 个） | 与参考项目一致 |
| 行走能力 | 直线行走、原地转向、坐下、挥手 | 基础步态集 |
| 表情 | 0.96" OLED，128×64 单色 | 参数化表情系统 |
| 交互 | 动作 + 表情 + 声音；V3 加语音与摄像头 | 逐版本递进 |

## 5. 硬件方案（摘要）

完整论证见评审文档，此处只保留结论：

| 编号 | 决策 | 结论 |
|---|---|---|
| D1 | 自由度 | 8 DOF（每腿 2 个舵机） |
| D2 | 主控 | ESP32-C3 SuperMini + PCA9685（16 路 PWM，余量最大） |
| D3 | 舵机 | A 档 SG90 ¥5.5 ／ B 档 MG90S ¥7.5，**必须 180° 版本** |
| D4 | 供电 | A 档有线 5V/3A；B 档 2S 18650 + 降压 |
| D5 | 结构 | 复用 sesame 的 11 件套 STL（Apache-2.0） |
| D6 | 固件 | 一期复用 sesame 架构改引脚，二期自研 |

**硬性约束（影响软件设计）**：

- **MCU 的 PWM 通道刚好用满**（8 路全给腿），但 **PCA9685 还剩 8 路空闲** —— 扩展舵机（尾巴、云台、夹爪）必须走 PCA9685，不能占 MCU 通道
- 8 舵机峰值电流 5.6–8 A，**软件必须限制同时动作的舵机数量**
- ESP32-C3 无 PSRAM，**端侧做不了视觉推理**，AI 必须跑在手机/电脑

### 5.5 扩展件与扩展接口

#### 5.5.1 这个决定很关键：主控选型顺带解决了扩展问题

我们在 D2 里选了 **ESP32-C3 + PCA9685**（而不是 ESP32-S3 直驱）。当时的主要理由是"不怕 PWM 通道用满"，现在再看，它带来一个额外好处：

| | ESP32-S3 直驱方案 | **ESP32-C3 + PCA9685 方案（已采用）** |
|---|---|---|
| 腿部舵机 | 占用 8 路 MCU PWM | 占用 PCA9685 的 8 路 |
| 剩余可用舵机通道 | **0 路**（加尾巴就要换方案） | **8 路空闲**（尾巴、云台、夹爪随便加） |
| 非舵机扩展 | 只能走 I2C/UART | 一样走 I2C/UART |

> **结论：选 PCA9685 不只是省钱，它把"可扩展性"一起买回来了。** 这是本方案相对于参考项目的一个重要优势，建议在评审文档中补记。

#### 5.5.2 扩展接口规范

**机械接口**

- 位置：**背部 1 个 + 头部 1 个**，共 2 个标准扩展位
- 固定方式：磁吸定位 + 2×M2 螺丝防脱（既能快速拆装，又不会甩飞）
- 电气连接：**4pin 弹簧针（pogo pin）**，免插拔线材，小朋友也能换

**电气接口**

| 引脚 | 定义 | 说明 |
|---|---|---|
| 1 | 5V | 独立限流 500 mA，带自恢复保险丝 |
| 2 | GND | |
| 3 | SDA | I2C 数据 |
| 4 | SCL | I2C 时钟 |

- 接口定义兼容 **Grove / DFRobot 生态**，市面上现成模块可以直接插
- 额外预留 1 路 UART（给摄像头、语音模块这类 I2C 带不动的外设）
- **供电预算**：舵机峰值已吃掉大部分 3 A，扩展件总额定电流必须 ≤ 500 mA；大功率扩展（摄像头 + 灯环同时开）由软件做分时调度

**软件**

- 上电扫描 I2C 地址 → 自动识别并加载对应驱动（插件式，不需要重新烧固件）
- 扩展件向固件注册"能力标签"（如 `distance` / `camera` / `sound` / `light`），玩法按能力匹配，不按具体型号匹配
- 未识别的扩展件进入"裸 I2C 模式"，供高级玩家自己写驱动

## 6. 设计规范

### 6.1 工业设计

| 项目 | 要求 |
|---|---|
| 形态语言 | 方正偏圆润的"方块宠物"，头部占比大以容纳表情屏 |
| 尺寸 | 最长边 ≤ 150 mm，可单手托起 |
| 材质 | PLA 打印，表面免打磨；配色以双色为主（主体色 + 关节色） |
| 配色方案 | 默认三套：奶白+橙、深灰+青、纯白+黑 |
| 关节设计 | 舵机可独立拆装，单腿故障 10 分钟内可换 |
| 可及性 | 螺丝统一 M2 规格，一把十字螺丝刀可全拆 |

### 6.2 表情系统设计（核心设计资产）

OLED 只有 128×64 单色，表达力受限，因此**不能靠贴图，必须靠参数化几何造型**。

**表情参数定义（12 维）**

| 参数 | 范围 | 作用 |
|---|---|---|
| `eyeOpen` | 0–1 | 眼睛开合（0 = 闭眼/困） |
| `eyeShape` | 0–1 | 圆眼 → 弯月眼 |
| `eyeWidth` | 0–1 | 眼睛横向拉伸（惊讶时变窄） |
| `pupilSize` | 0–1 | 瞳孔大小（放大 = 可爱/惊讶） |
| `gazeX` / `gazeY` | −1–1 | 视线方向，可跟随人脸或鼠标 |
| `browHeight` | 0–1 | 眉毛高度（生气时压低） |
| `browAngle` | −1–1 | 眉毛角度（愤怒/委屈） |
| `mouthOpen` | 0–1 | 嘴部开合（说话/惊讶） |
| `mouthCurve` | −1–1 | 嘴角弧度（笑 / 不开心） |
| `blink` | 0–1 | 眨眼触发 |
| `squint` | 0–1 | 眯眼（开心 / 怀疑） |

**基础表情预设（≥ 12 种）**：开心、大笑、生气、难过、困倦、惊讶、疑惑、害羞、无聊、专注、害怕、得意。

**设计原则**

1. **夸张优先**：单色小屏上的细微差别看不出来，幅度要夸张
2. **动作联动**：表情必须与动作同步（挥手时笑、被推倒时晕）
3. **平滑过渡**：表情切换要走缓动，不能瞬跳，否则显得机械
4. **可组合**：12 个参数可插值，理论上可生成无限表情，预设只是常用组合

参考实现：[orji123/Irisoled](https://github.com/orji123/Irisoled)（Arduino OLED 表情眼睛库）、[stack-chan/m5stack-avatar](https://github.com/stack-chan/m5stack-avatar)（M5Stack 表情渲染库）。

### 6.3 动作语言设计

动作库分三类，便于玩法组合：

| 类别 | 动作 | 用途 |
|---|---|---|
| **功能类** | 站立、前进、后退、左转、右转、趴下、起身 | 移动能力 |
| **情绪类** | 开心摇摆、生气跺脚、难过低头、害怕后退、得意转圈 | 情感表达 |
| **表演类** | 挥手、点头、摇头、伸懒腰、跳舞、装死、击掌 | 互动与内容创作 |

每个动作定义为**关键帧序列**，格式见 7.2，可被伴生应用可视化编辑。

### 6.4 反馈设计

| 通道 | 手段 | 要求 |
|---|---|---|
| 视觉 | OLED 表情 + 可选 RGB 灯 | 状态变化 100 ms 内可见 |
| 听觉 | 蜂鸣器 / 喇叭（C 档） | 开机、确认、报错、情绪音效各不同 |
| 动作 | 身体姿态反馈 | 收到指令先"抬头"确认再执行 |
| 触觉 | 可选触摸传感器 | 被摸头时表现开心 |

**原则：任何用户操作都必须在 200 ms 内给出至少一种反馈**，否则用户会以为死机。

### 6.5 桌面安全设计（掌上机器人特有的坑）

掌上级机器人和大机器人最大的区别是：**它天天待在桌子边缘、玻璃台面上、显示器旁边**。下面这些是这类产品真实会踩的坑，必须提前设计进去。

| # | 问题 | 为什么致命 | 设计对策 | 优先级 |
|---|---|---|---|---|
| 1 | **坠桌** | 桌面边缘摔落是小机器人第一大杀手，一次就断腿 | **悬崖检测**（向下红外对管或 ToF）：检测到悬空立即后退并停下 | **P0** |
| 2 | **打滑** | 玻璃 / 光滑桌面四足抓地力不足，走两步就偏 | 脚底贴硅胶垫；默认步态降速；提供"防滑模式"（更小幅、更慢） | P0 |
| 3 | **噪音扰人** | 舵机在安静办公室或夜里非常吵，会被嫌弃 | **静音模式**：降速降幅、暂停摇摆、只用表情和眼神表达 | P0 |
| 4 | **续航焦虑** | 8 舵机耗电，实测类产品普遍只有 20–40 分钟 | 电量表情化（没电时"犯困"）；低电自动趴下；支持可换电池 | P0 |
| 5 | **舵机发热** | 连续运动 20 分钟后 9g 舵机明显发烫 | 连续动作 15 分钟提示休息；可选温度监测自动降频 | P1 |
| 6 | **翻倒后起不来** | 8 自由度四足自己翻回来很难，卡住会让用户以为坏了 | 不硬做自恢复，改为**"蹬腿求助"动作 + 委屈表情**，把缺点变成萌点 | P1 |
| 7 | **舵机寿命** | SG90 属于耗材，扫齿是常态 | 结构上保证单舵机 10 分钟可换；官方卖舵机备件包 | P1 |
| 8 | **夜间误触** | 放桌上容易碰到，半夜突然动起来很吓人 | 静置 5 分钟自动"睡着"（呼吸灯 + 闭眼），被触碰才醒 | P1 |
| 9 | **多机互相干扰** | 朋友聚会两台一起玩，WiFi 会打架 | mDNS 命名 + 设备 ID + 频道错开；支持"多机同步"模式 | P2 |
| 10 | **线材易损** | 充电口、舵机线反复弯折断裂 | 扩展接口用 pogo pin 免插拔；线材走内部走线槽 | P2 |

> **产品判断**：第 1、3、4 条是"决定用户会不会长期玩"的三个关键。悬崖检测尤其重要——没有它，用户第一次摔坏就不会再玩了。这也是为什么我在扩展件清单里把它列为 P0。

## 7. 软件架构

### 7.1 三层架构

```
┌─────────────────────────────────────────────────┐
│  伴生应用（手机 / 电脑）                          │
│  视频动作提取 · 表情识别 · 动作编排 · 遥控 · 市场 │
└──────────────────┬──────────────────────────────┘
                   │ WiFi：HTTP JSON / WebSocket
┌──────────────────▼──────────────────────────────┐
│  机器人本体（ESP32-C3）                          │
│  动作解释器 · 舵机调度 · 表情渲染 · 姿态管理      │
└─────────────────────────────────────────────────┘
                   │ 可选
┌──────────────────▼──────────────────────────────┐
│  云端（可选）：LLM 对话 · 动作包市场 · 数据同步   │
└─────────────────────────────────────────────────┘
```

**为什么 AI 不放在机器人上**：ESP32-C3 没有 PSRAM，跑不动视觉模型；而手机算力是它的几百倍。把 AI 放端侧还能顺带解决隐私问题——**视频画面不出手机**，只传动作特征。

### 7.2 动作文件格式（.motion）

开放、可读、可编辑的 JSON 是关键设计资产（决定了 UGC 生态能不能起来）：

```json
{
  "name": "happy_wiggle",
  "version": 1,
  "duration_ms": 2400,
  "loop": false,
  "tracks": {
    "servo": [
      { "t": 0,    "ch": [90, 90, 90, 90, 90, 90, 90, 90] },
      { "t": 800,  "ch": [75, 105, 105, 75, 90, 90, 90, 90] },
      { "t": 1600, "ch": [105, 75, 75, 105, 90, 90, 90, 90] },
      { "t": 2400, "ch": [90, 90, 90, 90, 90, 90, 90, 90] }
    ],
    "face": [
      { "t": 0,    "expr": { "eyeOpen": 1, "mouthCurve": 0.8, "squint": 0.5 } },
      { "t": 2400, "expr": { "eyeOpen": 1, "mouthCurve": 0.8, "squint": 0.5 } }
    ],
    "audio": [ { "t": 0, "clip": "happy_01" } ]
  },
  "meta": { "author": "user", "source": "video_import", "tags": ["happy", "dance"] }
}
```

要求：

- 时间轴统一毫秒；舵机通道 0–7 对应固定物理位置（左右前腿 × 2 + 左右后腿 × 2）
- 角度为绝对角度（0–180），不是增量
- 播放时由固件做插值与限速（保护舵机）
- 文件可独立分享，构成"动作包"

### 7.3 通信协议

| 动作下发 | HTTP POST JSON | 简单可靠，够用 |
| 实时遥控 | WebSocket | 低延迟，双向 |
| 表情流 | WebSocket（10–20 fps） | 表情参数逐帧推送 |
| 设备发现 | mDNS | 免配 IP |
| 无网络 | 蓝牙 / AP 直连 | 出门也能玩 |

| 安全守护 | 掉电检测、舵机堵转超时、看门狗 |

## 8. AI 能力需求（核心新增）

### 8.1 能力一：视频导入生成动作

#### 8.1.1 用户故事

> 我用手机拍一段自己跳舞的视频（或从相册选一段），App 分析后生成一个动作包，点"同步"，机器狗就跟着节奏摆动、转身、点头，表情也一起变。

#### 8.1.2 动作哲学：**提取精华，再表达**

产品的目标不是让人的动作原样出现在四足机器人身上，而是**从视频里提取"动作精华"，再用机器人的身体重新表达一次**。

| 事实 | 我们的选择 |
|---|---|
| 人体 30+ 自由度，机器人只有 8 自由度 | 不做关节映射，只提取**运动特征** |
| 拓扑不同（人双臂双腿 vs 狗四肢） | 不做 IK 解算，只做**语义翻译** |
| 有些动作机器人根本做不了（跳跃、倒立、劈叉） | **降级为"摇摆 + 表情"**，不硬做 |
| 现有重定向项目（[GMR](https://github.com/YanjieZe/GMR)、[UMR](https://github.com/hanyang9/UMR)、[R2ET](https://github.com/Kebii/R2ET)）都是人形对人形 | 借鉴特征提取方法，不照搬映射结论 |

> **一句话原则：能做的就做，做不了的就摇摆。** 保证任何视频都能生成一个"看起来确实在跟着动"的结果。

这不是妥协，而是本产品的动作语言。就像卡通角色不会真的做物理动作，但观众完全看得懂它在表达什么——**机器人不需要跳得像，只需要动得对**。

#### 8.1.3 从视频里能提取的 7 类「精华」

| 精华维度 | 从视频里怎么提 | 机器人怎么表达 |
|---|---|---|
| **节拍 / 速度** | 音频能量包络 + onset 检测 → BPM | 动作播放速率、摇摆频率 |
| **能量 / 强度** | 肢体运动速度 × 幅度 | 摇摆幅度档位（小晃 / 中摆 / 大甩） |
| **方向** | 重心左右偏移、躯干朝向变化 | 前后行进、左右转向 |
| **周期性** | 动作片段自相关，判断是否循环 | 选循环类动作还是单次动作 |
| **高度变化** | 髋 / 肩在画面中的纵轴轨迹 | 站起 / 趴下 / 身体俯仰 |
| **情绪倾向** | 面部表情 + 动作柔和度（jerk 值） | 表情切换 + 动作刚柔 |
| **段落结构** | 音乐与动作的段落切分（前奏 / 高潮 / 收尾） | 动作编排的段落切换 |

#### 8.1.4 精华 → 机器人表达：映射表

这张表是"翻译词典"，是本能力最核心的设计资产，也是迭代时最该被反复打磨的东西：

| 视频里的动作 | 提取到的精华 | 机器人的表达 |
|---|---|---|
| 快速左右摇摆 | 高频 + 高能量 + 左右重心交替 | 原地左右摇摆，前腿大幅摆动 |
| 缓慢挥手 | 单侧上肢周期运动 + 低频 | 单只前腿反复抬起放下 |
| 转圈 | 朝向持续单向变化 | 原地转向 + 身体倾斜跟随 |
| 跳 | 垂直位移脉冲 | 前腿抬起 + 快速下蹲再起（不真跳） |
| 蹲下 | 高度持续下降 | 趴下 + 低头 |
| 摊手 / 比心 | 单次大幅上肢动作 + 停顿 | 抬头 + 开心表情 + 单腿抬起 |
| 正常走路 | 周期性 + 前进方向 | 直接行走 |
| 街舞连拍 | 高频 + 多方向 + 高能量 | 高频摇摆 + 快速转向 + 兴奋表情 |
| 倒地 / 躺平 | 高度骤降至最低 | 装死（机器人本来就擅长） |
| 完全识别不出 | 只剩节拍与能量 | 纯摇摆 + 表情随音乐变化 |

#### 8.1.5 兜底原则：**任何输入都必须有输出**

1. **能不降级就不降级**：能映射成真实动作的（走路、转向、趴下）优先走真实动作
2. **做不了就降级**：无法映射的一律落到"摇摆 + 表情"，幅度与频率由精华参数控制
3. **绝不失败**：即使姿态识别质量很差，也至少能仅凭节拍与能量生成一段律动，**不允许出现"分析失败，无法生成"**
4. **降级也要降得好看**：摇摆不是敷衍，要有起承转合（幅度包络 + 表情配合 + 收尾动作）

这条原则的产品意义：用户随手拍什么都能出结果，**成功率 100%**，这是玩法能传播出去的前提。

#### 8.1.6 三级实现路径

| 级别 | 方案 | 效果 | 工作量 |
|---|---|---|---|
| **L1 律动级** | 音频节拍 + 能量 → 驱动动作库律动 | 跟着节奏摇摆，已经能玩 | 小（1–2 周） |
| **L2 精华级** | MediaPipe 姿态 → 提取 7 类精华 → 查映射表 → 生成动作 | 能看出"在学视频里的动作" | 中（1–2 月） |
| **L3 风格级** | 3D 动作（GVHMR / MotionBERT）→ 风格向量 → 参数化步态或 RL 合成 | 表达更细腻，能带个人风格 | 大（3 月+） |

**落地顺序 L1 → L2 → L3。L1 就能撑起完整玩法，不要等 L3 才上线。**

#### 8.1.7 处理流程

```
视频文件（相册选择或现场拍摄）
  → 抽帧（10–15 fps 足够，不必逐帧）
  → 双路分析：
       A. 音频轨 → 节拍 / BPM / 能量包络
       B. 视频轨 → 人体姿态（MediaPipe Pose）→ 7 类精华特征
  → 精华特征 × 映射表 → 机器人动作原语 + 参数
  → 关键帧合成（插值 + 限速 + 平衡约束 + 兜底降级）
  → App 内预览（2D / 3D）
  → 用户微调（幅度档位、风格）→ 保存为 .motion
  → 下发机器人播放
```

#### 8.1.8 算力与延迟预算

| 环节 | 预算 | 说明 |
|---|---|---|
| 视频分析 | 离线，1 分钟视频 ≤ 30 秒 | 可接受，因为不是实时 |
| 用户预览与调整 | 30 秒内完成一次 | |
| 下发 + 播放 | 首帧 < 500 ms | 局域网 |

**重要：视频分析是离线批处理，不是实时流**，所以手机端纯 CPU 就能做，不需要 GPU，也不需要机器人端算力。

#### 8.1.9 参考实现

| 环节 | 参考 |
|---|---|
| 人体姿态估计 | MediaPipe Pose / BlazePose |
| 3D 动作提升 | GVHMR、MotionBERT |
| 重定向方法论（人形，供借鉴） | [GMR](https://github.com/YanjieZe/GMR)、[UMR](https://github.com/hanyang9/UMR)、[R2ET](https://github.com/Kebii/R2ET)、[robot_retargeter](https://github.com/ccrpRepo/robot_retargeter) |
| 舞蹈动作重定向 | [EverybodyDanceNow](https://github.com/carolineec/EverybodyDanceNow) |

### 8.2 能力二：面部表情传入

#### 8.2.1 用户故事

> 我对着手机摄像头做个鬼脸，机器狗的表情屏同步变出同样的情绪；我笑它也笑，我皱眉它也皱眉。

#### 8.2.2 技术路线

```
手机前置摄像头
  → MediaPipe FaceMesh（468 个面部关键点 + 52 个 blendshape 系数）
  → 表情系数计算（Kalidokit 转 ARKit 风格 blendshape）
  → 52 维 → 12 维降维映射（对齐 6.2 的表情参数）
  → 时间平滑（一阶低通 + 变化速率限制）
  → WebSocket 推送（10–20 fps）
  → 机器人 OLED 渲染
```

**关键组件**：[yeemachine/kalidokit](https://github.com/yeemachine/kalidokit)（5708 stars）——它把 MediaPipe 的 Face/Eyes/Pose 输出转成 blendshape 与骨骼运动学，正是"表情传入"最省事的一条路，且支持浏览器端运行。

其他可参考：[ci2cv/face-analysis-sdk](https://github.com/ci2cv/face-analysis-sdk)（表情迁移库）。

#### 8.2.3 52 维到 12 维的映射策略

| 机器人参数 | 来源 blendshape（示例） |
|---|---|
| `eyeOpen` | `eyeBlinkLeft` / `eyeBlinkRight` 反相 |
| `eyeShape` / `squint` | `eyeSquintLeft` / `eyeSquintRight` |
| `browHeight` | `browInnerUp`、`browOuterUpLeft/Right` |
| `browAngle` | `browDownLeft` / `browDownRight` |
| `mouthOpen` | `jawOpen` |
| `mouthCurve` | `mouthSmileLeft` / `mouthSmileRight` − `mouthFrownLeft/Right` |
| `pupilSize` | 由 `eyeWide` 加权推导（FaceMesh 不给瞳孔直径） |
| `gazeX` / `gazeY` | 由眼球关键点相对眼眶中心估算 |

#### 8.2.4 设计要点

1. **平滑优先**：原始表情系数抖动大，直接推送会让 OLED 抖成噪点。必须做低通滤波 + 最大变化速率限制。
2. **表情"转译"而非"复制"**：单色小屏表达力有限，要做**夸张化映射**（轻微皱眉 → 明显的眉毛角度变化）。
3. **延迟目标**：端到端 < 150 ms，超过 200 ms 用户就会觉得"不同步"。
4. **隐私**：默认只在端侧处理，**不上传视频帧**，只上传 12 维参数（可选关闭）。
5. **降级策略**：网络抖动时自动降到 5 fps 或退回预设表情，避免卡成静止脸。

#### 8.2.5 反向能力（机器人 → 人）

机器人也可以把自身情绪状态用表情表达出来（PAD 情感模型驱动），配合摄像头做人脸跟随（`gazeX/gazeY` 追人）。这条线不依赖 AI 模型，V2.0 即可实现。

### 8.3 能力三：语音交互

- 底座直接复用现有生态：[78/xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)（29889 stars，MIT）
- 硬件：C 档加麦克风 + 喇叭；A/B 档可先用手机语音，把指令转成动作下发（**零硬件成本**）
- 语音指令 → 动作映射表由伴生应用维护，用户可自定义"说这句话做什么动作"

### 8.4 能力四：音乐律动

- 输入：手机麦克风或音频文件
- 处理：节拍检测（BPM + onset 检测，可用 aubio / librosa / 浏览器端 Web Audio）
- 输出：节拍触发动作库中的律动动作，强度随音量变化
- 这是**性价比最高的玩法**：实现成本低、观赏性强、不依赖复杂模型，建议作为 V2.0 的引流功能

### 9.2 玩法设计原则

1. **一部手机就能加一个新玩法**：所有玩法的算力都在伴生应用，机器人只做播放，这样玩法迭代不需要用户改硬件
2. **先做好"出片"的玩法**：视频律动和表情镜子都有强传播性（人 vs 机器的反差），放在 V2.0 最前面
3. **每种玩法都有"第一次就成功"的路径**：不要求用户先学编程，默认动作包开箱可用
4. **玩法之间共享资产**：动作包、表情包、语音指令表都是同一套格式，互相可组合

### 9.3 留存设计（轻量）

- 每日首次互动给一个特殊表情
- 解锁机制：连续使用解锁隐藏动作
- 生成分享图：一键导出"机器人今天的心情"

> 说明：养成与留存属于加分项，不是本项目的核心目标，不做重度游戏化。

### 9.5 竞品玩法对标

掌上机器人这个赛道的经典产品，各自把某一种玩法做到了极致。我们对标它们的"长处"，而不是拼参数。

| 产品 | 定位 | 值得借鉴的玩法 | 我们的取舍 |
|---|---|---|---|
| Anki Cozmo / Vector | 桌面机器人 | 表情 + 性格 + 小游戏（猜方块）、自发行为、情绪状态机 | **重点借鉴**：把表情当第一交互语言；我们不做复杂 SLAM |
| Sony Aibo | 宠物机器人 | 养成、性格成长、被摸的反应 | 借鉴"摸头 → 情绪变化"，但**不做云端记忆**（隐私与成本） |
| Petoi Bittle / Nybble | 开源四足 | 编程、竞技、模块化传感器、赛事社区 | **直接对标**：我们要在"AI 玩法"上做出差异 |
| Stack-chan | 桌宠 | AI 对话、头像动画、M5 生态扩展 | 借鉴表情库设计与生态思路；语音用现成小智方案 |
| Sphero / mBot | 教育机器人 | 图形化编程、巡线、课程体系 | 借鉴图形化编程，**不做完整课程体系**（非本期目标） |
| DJI RoboMaster S1 | 竞技机器人 | 对战、赛事、UGC 内容生态 | 借鉴"动作包市场"的思路，规模做小 |
| microduck / Open Duck Mini | 开源双足 | RL 训练、物理仿真、社区复刻 | 借鉴其"仿真 + 开源"的做法，V3 再考虑 |

**一句话结论**：这个赛道没人同时做到"**便宜 + 会走 + 会学你动作和表情 + 玩法靠软件扩展**"。我们的差异点就是这四件事的交集。

### 12.1 产品系列化（建议）

同一套硬件 + 不同扩展件组合，可以覆盖完全不同的用户群，**不需要为每个系列重新设计主板**：

| 系列 | 面向人群 | 配置 | 参考价 | 卖点 |
|---|---|---|---|---|
| **基础版** | 入门 DIY / 极客 | A 档（有线、塑料齿） | ≈ ¥106 | 最便宜，先跑通 |
| **宠物版** | 桌宠用户 / 送礼 | B 档 + **悬崖检测 + 触摸 + 灯环** | ≈ ¥180 | 敢放桌上、能摸头、有情绪灯 |
| **竞技版** | 玩家 / 内容创作者 | B 档 + 摄像头 + 踢球附件 + 场景套装 | ≈ ¥220 | 足球、竞速、手势遥控 |
| **教育版** | 学校 / 培训机构 | B 档 + 图形化编程 + 场景套装 + **舵机备件包** | ≈ ¥260 | 摔得起、修得快、有课程 |
| **开发者版** | 二次开发 / 科研 | B 档 + 全套传感器 + 开放扩展接口 | ≈ ¥300 | 接口全开，适合做研究 |

**两个值得单独卖的 SKU**：

1. **舵机备件包**（SG90 × 4 + 螺丝）：舵机是耗材，扫齿是常态。提供备件包能显著降低"摔了就不玩了"的流失。
2. **扩展件单卖**：悬崖检测、灯环、触摸这三个 P0 件单价低、通用性强，适合单独零售做复购。

> 说明：系列化不属于本期承诺，仅作为成本结构允许时的产品化方向。

## 14. 验收标准（DoD）

V1.0：

1. 稳定站立 5 分钟不摔，连续行走 1 米
2. 网页可控制全部 P0 动作，延迟 < 500 ms
3. OLED ≥ 6 种表情，与动作联动
4. 连续运行 30 分钟无死机、无复位
5. A 档物料成本 ≤ ¥115
6. **悬崖检测有效**：在 60 cm 高的桌面上走向边缘时，必须在悬空前停住（B+ 配置）
7. **静音模式可用**：静音模式下不产生摇摆噪音，仅用表情与小幅动作表达

V2.0 追加：

8. 音乐打拍：节拍与动作同步误差 < 200 ms
9. 表情镜子：端到端延迟 < 150 ms，连续 3 分钟不抖动
10. 动作编排：用户可在 10 分钟内做出一个自定义动作并分享
11. 上述玩法**全部在飞行模式下可完成**（离线可用）
12. **扩展件可热插拔识别**：接上灯环或触摸件后无需重新烧固件即可生效
